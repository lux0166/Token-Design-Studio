# 0.4.0 — Implementation and acceptance record

**Overall status: awaiting native client and comparative evaluation acceptance.** The code and local packages implement workflow 1.4.0 / task schema v2. This document does not declare the whole release accepted or published.

## Implemented behavior

- Each criterion has a stable ID and sourced decision links; passed acceptance checks link criteria to actual artifact records. Broken references, unsupported pass records and unresolved blockers prevent completion.
- Separate plan and implementation SHA-256 snapshots preserve pre-code checks across code edits while invalidating affected behavior/render evidence. A local report binds the current dossier, snapshots and recorded evidence hashes.
- The bundled helper supports upgrade with backup, snapshot, verify, root boundaries, file existence/hashes and structure-only diagnostics. It does not execute commands from a dossier. Refreshing snapshots never restamps old checks or artifact hashes.
- `local-ui` and token changes use compact notes and affected evidence. Screen and reference work retain stronger requirements; grill-me verifies specification coverage without requiring code/render.
- HTTP and the same 17 MCP tools accept legacy v1 and v2 task inputs. New unversioned drafts default to v2; clients intentionally sending legacy records should specify schemaVersion 1. Completed legacy history remains labeled under the old policy. Editing reopens a record; new completion requires v2. Store format migration backs up v1 before the first atomic v2 write and does not change theme revisions.
- Studio shows criterion/source/check/evidence links, report level/time, upgrade guidance and completion issues. There is no filesystem access, remote image fetch or background synchronization in the server.
- Skill installers provide read-only doctor and explicit `--adopt-known`. Pinned upstream hashes and documented legacy icon-policy variants are accepted; unknown edits are refused. Locking, staging, backups and interrupted-install recovery remain shared.

## Remaining gates and limits

Native Antigravity IDE/app testing is user-assisted because native UI automation is unavailable. The user has agreed to run the prepared smoke prompt. Until the actual dossier and client evidence are supplied and checked, this gate remains pending. A successful `agy` CLI exit is not an IDE/app pass.

The eight native workflow comparisons and four behavior cases are tracked separately in [the 1.4.0 evaluation record](../evaluation/1.4.0/REPORT.md). Supporting CLI diagnostics use a restricted prototype/text-reference harness and cannot replace native image-reference evaluations. Model defaults may be unreported, so no causal quality/speed claim is made.

The file checker's input list is explicit; it adds enclosing package manifests/lockfiles but does not infer an entire dependency graph. Source edits are detected on the next local verify and sync, not continuously. Local reports are client-provided: Studio can enforce consistency, not authenticate image inspection, user intent, test truth or aesthetic quality. Files are limited to 32 MB each and 64 MB per verification.

No npm publication or GitHub merge has been performed. Artifact checksums and the final acceptance matrix are recorded after the remaining checks; preserve the pending status until both native client and comparative gates are met.
